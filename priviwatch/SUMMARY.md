# Privwatch Summary

## 1) What the tool does
Privwatch monitors real-time privilege changes on a Linux/Android kernel by tracing `commit_creds()` and reporting changes in:
- UID/GID
- Effective capabilities
- PID namespace inode
It emits events only when a privilege change occurs, reducing noise.

## 2) High-level architecture
- Kernel space (eBPF): kprobe on `commit_creds` captures old vs new credentials and pushes an event to a ring buffer.
- User space: libbpf-based loader reads ring buffer events, formats output with severity hints, and prints a one-line summary.

Data flow:
1. Process calls `commit_creds(new_cred)`.
2. eBPF program reads old creds from current task, new creds from the function arg.
3. If something changed, an event is emitted to a ring buffer map.
4. User space polls the ring buffer and prints the change.

## 3) Kernel-side details (privwatch.bpf.c)
- Probe: `SEC("kprobe/commit_creds")` with `BPF_KPROBE(trace_commit_creds, struct cred *new_cred)`.
- Old credentials read via `task->cred`, new credentials from `new_cred`.
- Reads:
  - `uid.val` and `gid.val` from both creds.
  - effective capability set (`cap_effective`).
  - parent PID via `task->real_parent->tgid`.
  - PID namespace inode via `task->nsproxy->pid_ns_for_children->ns.inum`.
- Event gating: only submit if UID, GID, or capabilities changed.
- Map: ring buffer (BPF_MAP_TYPE_RINGBUF) with 16 MB size (1 << 24).

Capability read implementation:
- Uses a local `struct cap_words { __u32 val[2]; }` and `bpf_probe_read_kernel()` to read the full `kernel_cap_t` object.
- This avoids CO-RE relocation on `kernel_cap_t.val`, which is a known issue across kernel versions.

## 4) User-space details (privwatch.c)
- Uses libbpf skeleton generated by `bpftool gen skeleton`.
- Loads and attaches the BPF program, then creates a ring buffer reader.
- Prints:
  - Timestamp (local time)
  - Severity hint (INFO/WARN/ALERT)
  - PID, PPID, comm, PID namespace inode
  - Only the fields that changed (uid/gid/caps)

Severity logic:
- INFO by default.
- WARN: non-root to root transition (old uid != 0, new uid == 0).
- ALERT: Android app UID (greater than 10000) to root, highlighting likely privilege escalation.

Capability diff output:
- Prints raw hex diff and highlights high-risk gains such as CAP_SYS_ADMIN, CAP_SETUID, CAP_SETGID, CAP_SYS_PTRACE.

## 5) Build and run (Makefile)
- Builds libbpf locally from ../third_party/libbpf.
- Requires:
  - clang (for BPF)
  - gcc (user space)
  - bpftool in PATH
  - vmlinux.h for target arch in ../third_party/vmlinux/<arch>/vmlinux.h

Typical steps:
- `make`
- `sudo ./privwatch`

## 6) What is new or notable vs existing tools
- Focused on privilege transitions rather than syscalls or process creation, so it highlights security-relevant events with low noise.
- Includes capability-diff reporting, which many basic cred monitors skip.
- CO-RE safe capability read: reads `kernel_cap_t` as a plain local struct to avoid relocation failures on `kernel_cap_t.val` across kernels.
- PID namespace awareness (ns inode), which is useful on Android containers / isolation setups.
- Severity classification tuned for Android UID ranges (uid > 10000).

## 7) Likely supervisor questions + answers (concise)
Q: Why `commit_creds`?
A: It is the canonical kernel point where credentials are installed. Capturing here ensures we see real privilege transitions, not just intent.

Q: Why ring buffer vs perf buffer?
A: Ring buffer is simpler and more efficient for variable-rate events, with lower overhead and better backpressure support.

Q: How do you avoid kernel version issues with capabilities?
A: The capability set is read using `bpf_probe_read_kernel()` into a plain local struct, avoiding CO-RE relocation on `kernel_cap_t.val`.

Q: How do you reduce noise?
A: The eBPF side filters out events where UID, GID, and caps are unchanged.

Q: What can this detect on Android?
A: Unexpected transitions from app UIDs (>= 10000) to root, capability gains like CAP_SYS_ADMIN, and any credential changes across namespaces.

## 8) Known limitations / considerations
- kprobe on `commit_creds` requires kernel support for BPF + kprobes and may need root to load.
- If a kernel uses different credential structs, CO-RE helps but still depends on `vmlinux.h` correctness.
- Outputs are event-driven; it does not reconstruct full process ancestry or history beyond PID/PPID.
